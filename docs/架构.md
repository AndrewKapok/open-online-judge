# 在线评测系统架构文档

采用MSVC工具链

## 1. 整体架构

系统采用前后端分离设计，核心组件包括：

- **用户浏览器**：访问静态页面与 API
- **oj 程序**：统一的可执行程序，提供两种运行模式：
  - **Web 服务器模式**：通过 `oj start` 启动后台 Web 服务器
  - **CLI 模式**：通过 `oj [command]` 执行管理命令
  - **退出命令**：通过 `oj exit` 退出后台运行的 Web 服务器
- **核心逻辑层**：封装所有业务规则，为 Web 服务器和 CLI 提供统一调用入口
- **文件系统**：存储题目、测试数据与用户代码
- **SQLite 数据库**：存储用户账户、提交记录等持久化数据
- **判题单元（内置）**：在核心进程内编译运行代码，评测提交，不支持扩展为独立集群

请求与命令流转路径：

1. 静态资源请求 → Web 服务器（直接返回静态页面）
2. 普通用户 API 请求 → Web 服务器 → 转发给核心层处理
3. 管理员命令 → CLI → 直接调用核心层接口，执行创建比赛、修改题目、管理用户等操作
4. 提交评测 → 核心层写入消息队列，内置判题单元消费任务并更新结果

分层：

1. 用户输入层
   1. Web 服务器: 用户 API 调用
   2. 管理员 CLI
2. core 内核层
   核心业务逻辑（包含 Session 管理、权限校验、业务处理等）
4. 文件系统，SQLite, JSON, judger 评测模块

## 2. 前端

### 2.1 路由与页面设计

- **根路径** **`/`**
  - 未登录：302 重定向到 `/login`
  - 已登录：返回 Dashboard 页面
- **登录页** **`/login`**
  - 若登录成功，302 重定向到首页 `/`
  - 提供注册与登录表单，对接后端 `/api/v1/register`、`/api/v1/login`
- **Dashboard（首页）**
  - 展示当前登录用户名
  - 按状态分组展示比赛：已开始、即将开始、已结束
  - 显示距开始时间、已开始时长、结束时间等
  - 点击比赛可进入对应比赛页面
  - 顶部导航栏提供到比赛列表、用户设置等的入口
- **比赛路由** **`/contest`**
  - 列表页按时间倒序展示：已开始 > 即将开始 > 已结束
  - 进入具体比赛 `/contest/{contest_id}`：显示比赛开始时间、赛制、题目数量等概况
  - 比赛内子页面：
    - `/contest/{id}/problem/{problem_id}` 题目详情与提交入口
    - `/contest/{id}/rank` 排行榜
    - `/contest/{id}/submissions` 提交记录
- **用户设置**：可修改密码等，对接 `/api/v1/user/profile/update`

## 3. oj 程序

oj 是系统唯一的可执行程序，提供两种运行模式：

### 3.1 Web 服务器模式

- **启动命令**：`oj start`
- **功能**：启动后台 Web 服务器，监听指定端口
- **职责**：收发 HTTP 请求，返回静态页面和 JSON 响应
- **进程**：后台运行，不阻塞终端

### 3.2 CLI 模式

- **命令格式**：`oj [command] [arguments]`
- **功能**：管理员本地执行管理命令
- **职责**：直接调用核心层接口

### 3.3 退出命令

- **命令**：`oj exit`
- **功能**：退出后台运行的 Web 服务器

## 4. 后端路由与服务

### 4.1 Web 服务器职责

- 接收所有 HTTP 请求（静态资源和 `/api/v1/*` API 请求）
- 收发网络请求
- 解析 HTTP 请求参数和 Body
- 解析 Cookie 提取 Session ID
- 将 Session ID 传递给核心层进行验证
- 将核心层处理结果构造为 HTTP 响应返回

### 4.2 核心逻辑层

核心逻辑层将业务规则封装为内部接口，供 Web 服务器和 CLI 共同调用，避免逻辑重复。主要职责包括：

- 用户注册、登录认证
- Session 验证、权限校验、销毁
- 比赛创建、修改、删除
- 题目添加、移除、配置更新、测试数据上传
- 提交评测入队、结果查询、排名计算
- 缓存主动失效、判题配置读取与更新等
- 消息队列管理（投递、消费、状态跟踪）

### 4.3 进程间通信

系统内部模块（如判题单元）通过 Unix Domain Socket 配合守护进程进行通信，实现高性能的异步任务传递和状态同步。核心层对判题单元的调用均采用该机制。消息序列化使用 rapidjson，采用 JSON 格式传输。消息队列、Session 管理、状态跟踪等功能由核心层内部实现。

## 5. 后端数据库

### 5.1 用户账户与密码

- 存储引擎：SQLite（通过 SQLite3 C API 操作）
- 密码采用加盐哈希存储，不保存明文
- 支持自注册与管理员通过 CLI 集中管理

### 5.2 Session 管理

- 完全由核心层内部管理，不落数据库
- 登录成功后生成 Session ID，通过 `Set-Cookie` 下发
- 使用 `std::unordered_map<std::string, SessionData>` 存储，`std::mutex` 保证并发安全
- Session 在服务关闭后自动失效，无需持久化
- 客户端通过 Cookie 携带 Session ID，服务端手动解析 HTTP Header 提取

### 5.3 代码与题目存储（文件系统）

采用清晰的目录结构，便于管理与备份：

```
数据根目录/
├─ contest_{id1}/
│  ├─ problems/
│  │  ├─ problem_{id1}/
│  │  │  ├─ problem.md       # 题面描述
│  │  │  ├─ config.json      # 题目配置（测试点数量、时空限制、输入输出方式、编译参数、比对方式等）
│  │  │  └─ testdata/        # 测试数据
│  │  │     ├─ 1.in / 1.out
│  │  │     ├─ 2.in / 2.out
│  │  │     └─ ...
│  │  └─ problem_{id2}/
│  │     └─ ...
│  └─ submissions/
│     ├─ user_{user_id}/
│     │  ├─ problem_{id1}/
│     │  │  ├─ submission_1.cpp
│     │  │  ├─ submission_2.cpp
│     │  │  └─ ...
│     │  └─ problem_{id2}/
│     └─ user_{user_id2}/
├─ contest_{id2}/
└─ ...
```

### 5.4 提交记录存储（SQLite）

每条提交记录包含以下字段：

- 提交 ID（主键）
- 用户 ID
- 题目 ID（由竞赛 ID + 题目 ID 唯一确定）
- 提交时间
- 代码文件路径（指向文件系统中实际存储位置）
- 评测结果详情：每个测试点的通过/失败状态、得分、时间、内存等

## 6. 判题单元（内置，不支持扩展）

判题功能以内置单元形式集成在核心进程中。系统启动时即初始化固定数量的工作线程，由消息队列驱动评测任务，满足中小规模并发需求。

### 6.1 编译与执行

- 代码提交后，判题单元从消息队列拉取任务
- 执行测试用例，将结果回写至提交记录并更新排名

### 6.2 评测消息队列

由核心层内部管理，支持两种调度模式：

1. **实时 FIFO 模式**\
   提交即评测，按提交时间顺序分配判题工作线程。
2. **批量评测模式**\
   缓存一定时间后，将同一题目所有待评测代码集中调度，可减少测试数据的重复拷贝开销。\
   判题单元内部支持：
   - 轮询分配任务
   - 或固定由一个工作线程负责同一题目，评测完成后再协助其他题目

管理员可通过 CLI 根据系统负载选择或切换模式。

### 6.3 判题单元监控

- 判题单元的运行状态由核心层动态跟踪
- 配置信息从文件系统 JSON 加载，包含固定数量的工作线程数
- 管理员可通过 CLI 查看判题负载、队列状态、单个任务进度等，也可取消队列中的任务

***

以上标准确保前端、后端、CLI 与判题单元之间协同工作，实现低延迟、可维护的在线评测系统。
